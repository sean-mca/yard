# Migrating to v1.11

v1.11 adds version-aware codegen for Airflow 3.0. The change is fully additive -- no existing config fields are renamed or removed. AF2 configs without an explicit `airflow.version` field continue to produce byte-identical output.

## What changed

Five areas of emitted DAG output now vary by Airflow version. All are controlled by a single new config field (`airflow.version`).

| Area | AF2 (default) | AF3 (`version: "3"`) | Notes |
|------|---------------|----------------------|-------|
| `airflow.version` field | Not present (implicit `"2"`) | `version: "3"` in any cascade layer | New config field on `AirflowSection`. Default `"2"`. See [configuration reference](../configuration.md). |
| Asset trigger alias | `trigger: { dataset: { uri: ... } }` | Both `dataset` and `asset` keys accepted | `asset` is a parse-time alias; serialization always emits `dataset`. Either key works regardless of version. |
| Dataset / Asset codegen | `from airflow.datasets import Dataset` / `Dataset(uri)` | `from airflow.sdk import Asset` / `Asset(uri)` | Class name and import path change. Internal Rust types (`DatasetTrigger`, `SingleSource::Dataset`) are unchanged. |
| Operator imports | `from airflow.operators.bash import BashOperator` / `from airflow.operators.empty import EmptyOperator` | `from airflow.providers.standard.operators.bash import BashOperator` / `from airflow.providers.standard.operators.empty import EmptyOperator` | AF3 moves core operators to `providers-standard`. `GlueJobOperator` import is unchanged across versions. |
| Version banner | `apache-airflow >= 2.9`, `providers-amazon >= 8.13.0`, `aiobotocore >= 2.1.1`, Triggerer required | `apache-airflow >= 3.0`, `providers-amazon >= 9.0.0`, `providers-standard` | Event-driven DAGs carry a header comment declaring the version contract. |

## Upgrading to AF3

### Step 1: Set `version: "3"` in your config cascade

Add `version: "3"` to the `airflow:` block at whichever cascade layer applies -- `dag.yaml` for a single DAG, or `yard.yaml` / `account.yaml` / `region.yaml` to apply across a scope.

**Before:**

```yaml
# dag.yaml
airflow:
  schedule: "@daily"
  owner: data-team
  dags_bucket: my-mwaa-dags
```

**After:**

```yaml
# dag.yaml
airflow:
  version: "3"
  schedule: "@daily"
  owner: data-team
  dags_bucket: my-mwaa-dags
```

The field inherits through the config cascade like any other `AirflowSection` field. A `version: "3"` in `yard.yaml` applies to every DAG in the project unless overridden at a more specific layer.

### Step 2: Verify with `yard plan`

Run `yard plan` and inspect the generated DAG output. Confirm that:

- Import lines show `from airflow.sdk import Asset` (not `from airflow.datasets import Dataset`)
- Operator imports show `from airflow.providers.standard.operators.bash import BashOperator` (not `from airflow.operators.bash import BashOperator`)
- The version banner at the top of event-driven DAGs references `apache-airflow >= 3.0`

### Step 3 (optional): Use the `asset` trigger alias

AF3 users may prefer `asset` over `dataset` in trigger blocks for clarity. Both keys parse identically.

```yaml
# dag.yaml -- AF3 style
airflow:
  version: "3"
  trigger:
    asset:
      uri: s3://example-bucket/raw/orders/
```

This is cosmetic -- `asset` is a parse-time alias for `dataset`. Serialization always emits `dataset` regardless of which key was used in the YAML source.

## Hash drift on first apply

Adding `version: "3"` to a previously-deployed DAG changes the serialized `AirflowSection` (the `version` field goes from `None` to `Some(V3)`), which produces a one-time state-hash change on the first `yard apply` after the upgrade. This is expected and harmless -- the same HASH-03 behavior documented in the [v1.6 migration guide](v1.6.md#one-time-post-upgrade-drift-hash-03). DAGs that do NOT add `version` produce identical hashes because the field uses `skip_serializing_if = "Option::is_none"` and defaults to `None`.
