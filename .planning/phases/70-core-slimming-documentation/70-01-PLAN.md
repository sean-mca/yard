Implement custom Serialize for JobType: destructure Plugin(s) and call serializer.serialize_str(s). This preserves wire format -- state files store "glue" not {"Plugin":"glue"} per Pitfall 1.

Implement custom Deserialize for JobType: deserialize a String via String::deserialize, wrap in Plugin variant.

Rewrite Display impl: destructure Plugin(s), write the inner string.

Rewrite FromStr impl: reject empty strings with bail, wrap non-empty input in Plugin(s.to_string()).

Remove the doc comment referencing "Adding a fourth job type requires..." since types are now dynamic.

Add new doc comment explaining JobType::Plugin(String) enables dynamic provider resolution per D-03.

Update existing JobType tests in the #[cfg(test)] mod tests block (around line 1020-1066):
- Tests that construct JobType::Glue/Emr/Bash must use JobType::Plugin("glue".to_string()) etc.
- Serde round-trip tests must verify that serializing Plugin("glue") produces the string "glue" and deserializing "glue" produces Plugin("glue")
- FromStr tests must verify that "glue".parse::<JobType>() returns Plugin("glue") and "".parse::<JobType>() returns Err
- Display test must verify Plugin("glue").to_string() == "glue"

Search the entire yard-structs crate for any other uses of JobType::Glue, JobType::Emr, JobType::Bash and update them to Plugin("glue".to_string()) etc. Key sites:
- diff.rs test fixtures (around line 122: job_def_with_trigger uses JobType::Bash -- this is in yard-core but references the yard-structs type)
- Any test helpers that construct JobDefinition with a specific job_type

Note: the Copy trait loss means every call site that implicitly copied a JobType must now use .clone() or borrow with &JobType. The compiler will surface these. Fix them in this task within yard-structs only. The yard-core and yard-cli fixes happen in subsequent tasks.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-70-01 | Tampering | JobType deserialization | low | accept | JobType::Plugin(String) accepts any non-empty string; invalid provider names produce an actionable error at plugin download time when the binary is not found. Input validation is at the provider-resolution layer, not the type layer. |
| T-70-02 | Information Disclosure | Migration error message | low | mitigate | D-01 error message references docs/reference/migrations/v2.0.md by name -- gives users the upgrade path without exposing internal state. |
| T-70-03 | Denial of Service | Removed codegen/validation | low | accept | Codegen and provider-specific validation move to plugin binaries which are already sandboxed by process isolation (Phase 66 D-18). Core structural validation remains unchanged. |
| T-70-SC | Tampering | npm/pip/cargo installs | low | accept | No new packages installed in this plan. Only removing dependencies (aws-sdk-glue, aws-sdk-emr, tera). Attack surface strictly decreases. |
</threat_model>
